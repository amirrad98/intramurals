# LeagueFlow intramurals review and implementation

## Outcome and scope

This review prepares LeagueFlow 1.1.0 for review and staging installation. It addresses the operational issues in Zoe's 15–21 October 2026 emails and rebuilds the calendar/block interactions using the requested CampusManager reference.

The implementation is based on LeagueFlow commit `8c833d6f7e2850e6b861812172cab97f3c687d3a`. The supplied older source archive was also inspected to distinguish existing fixes from defects still present on current main. The CampusManager reference is pinned to `ac56cd12d05e7e37be21379845a58c3128705d4e`.

Reviewed areas include the WordPress administration screens, Gutenberg attributes and server preview, frontend calendar and portal scripts, public collection APIs, result/standings/knockout services, scheduling, team/player identity permissions, request reconciliation, registration flows, packaging and update discovery. Native WordPress, HTTP and DOM regression tests exercise the changes. The review is not a claim that every possible host, theme, integration or browser combination has been certified.

**Production was not accessed or changed.** The exact deployed version, affected Nov 29–Dec 7 records and production block settings were not available. No waiver attachment or approved Code of Conduct text was supplied. Browser rendering and a real Gutenberg interaction session could not be completed because the available browsers could not reach the isolated WordPress server. These limits remain explicit throughout the evidence.

## Interface decisions

The Sports Calendar block retains LeagueFlow's data model and block identity. CampusManager's useful interactions are adapted: month/week/day/list, direct date navigation, search, visitor filters, sidebar/dropdown/popover day details, left/right sidebar, cost visibility, event ordering and list batches. Google and ICS exports remain, with Outlook added. Existing time-grid overlap lanes remain covered by regression tests.

The calendar exposes outcomes people can act on: loading the chosen dates, no matching events, a failed request that can be retried, or more list events available. Public previews do not show private records merely because the editor is signed in. Every block has independent state and dialog/panel IDs. Keyboard focus, Escape behavior, labels and announcements are verified at DOM level; actual theme contrast and mobile visual fit still need browser review.

The administration improvements concentrate on task clarity: match date versus WordPress publication date, explicit finalization, why a result was excluded, which referee can see which match, whether that assignment can submit a score, which documents are required, and which already-placed requests will close. The new Staff guide is shipped in the plugin so staff need not consult the repository for routine tasks.

## Important behavior and compatibility

- **Season scope:** Blank/current uses the configured current season. Explicit `all` means every season. These choices are now labelled accurately in the editor. A calendar scoped to a team shows its matches, not unrelated drop-ins.
- **Results:** Both main scores must be valid non-negative integers. Zero is a real value, not an empty field. Finished status is intentional; entering optional sport notes does not finalize a result. Knockout fixtures are excluded from league tables.
- **Concurrent editing:** Staff match metadata, referee results, bulk status changes, scheduling and target bracket updates share result locks. A stale staff/referee score form cannot silently overwrite a changed result. Ordinary WordPress post publication/taxonomy edits remain governed by the WordPress save lifecycle; the metadata form token does not claim to roll those core writes back.
- **Referee storage:** Atomic result/evidence submission requires InnoDB for post metadata. Unsupported storage fails with an explanation rather than saving a partial final result. Staff retain normal WordPress administration access.
- **Documents:** Pasted approved text is retained as a sanitized snapshot. A linked PDF is retained as its URL/version, not its file bytes. Replacing a PDF at the same URL without a new version cannot be detected. Changing document identity/content requires acknowledgement again.
- **Existing participants:** Installation neither invents historical acceptance nor removes rosters. Staff and captains cannot accept on behalf of others. Manual additions can still be reviewed separately; acknowledgement status is not a complete participation-eligibility system.
- **Requests:** Generic core REST edits/deletes of join requests are deliberately blocked. Integrations that changed raw request records must use the authoritative workflow. Staff REST reads are preserved.
- **Distribution:** The runtime remains WordPress-native and does not depend on CampusManager being installed or bundle its React application. Existing content and shortcode names remain. The prepared version is 1.1.0, with no tag/release publication implied by the branch.

## Verification

The new regression suites use actual plugin code and a disposable WordPress installation, not mock replacements of business logic. Outbound registration mail is intercepted in tests. Concurrency checks include a second database connection and deliberate state changes immediately before lock acquisition.

The release workflow runs PHP syntax/helper checks on PHP 8.1–8.4, JavaScript DOM suites in three timezones, deterministic build/publication tests, and native integration on WordPress 6.5 and current stable. It tests an installed built ZIP; update testing must not run against a working-tree symlink because `Plugin_Upgrader` replaces the installed directory.

Local verification and the resulting branch CI are recorded in the pull request. The notable local suites include:

The 12 calendar DOM suite executions (four suites × three timezones), seven consent-draft assertions, ten Python packaging/publication tests, PHP helper checks and syntax checks also passed. ### Before production installation is accepted

1. Install the built review package on staging with a copy of the intended theme/settings. Open the existing calendar page and editor at desktop and phone widths, use keyboard navigation and verify at least two calendar blocks on one page.
2. Compare the actual Nov 29–Dec 7 soccer records with the public calendar under the deployed page's exact settings. Verify the host uses current named-timezone data and that a known local start time exports to the intended UTC instant; the review environments demonstrated that older and newer Vancouver timezone databases can disagree for these future dates (see [IANA's 2026b release notes](https://www.iana.org/time-zones/releases/2026b)). Purge the actual page/CDN cache if it serves old HTML.
3. Review the existing volleyball scores, league format and point rules. Finalize only results known to be complete; confirm the table under the intended season/competition filters.
4. Configure UNBC's approved waiver and Code of Conduct documents, their versions and a renewal communication plan. Test one participant and one referee account with the intended permissions.
5. Publish a stable release only after those acceptance checks and required CI succeed. No merge, tag, public release or live installation is performed by this review branch itself.
